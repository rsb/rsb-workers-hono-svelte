# Authentication research · workers-hono-svelte

Nov 5, 2026 · @Rob

## Summary

Build authentication as a gate in the api Worker, keep sessions as rows in D1, hand-roll the primitives rather than adopt a framework, and treat a separate auth Worker as a deployment choice to make later, not now. The five provisional decisions all survive; three are amended, and the amendments (a `channel` gate before `authenticate`, processes as the layer that crosses areas, and `access.md` split into `requires` and `scope`) are the findings that change the story.

The recommended architecture, in chain order. Gates in the api: `requestId`, `bodyLimit`, `channel` (origin and content-type discipline for cookie-bearing unsafe requests), `authenticate` (one D1 statement joining `sessions` to `users`, run on the primary; an unknown cookie becomes `anonymous` with a clear-cookie hint, an unknown bearer token is refused, a disabled user is refused). The BFF sets a `__Host-` cookie on its own host and forwards the browser's request over the service binding; it decides nothing. `sessions.start` returns the token in the envelope and each delivery stores it its own way (cookie, CLI keyring). The access runner applies `requires` before validation; the operation passes a typed `scope` to the store; the store reports facts. Sign-up, disable and email verification are processes because they cross `users` and `auth`. Passwords hash with Argon2id via module-imported WASM on the Paid plan; passkeys use `@simplewebauthn/server`; Google OIDC and magic links are about a hundred lines each; admin can sit behind Cloudflare Access on its own hostname. Every number above has a budget test: one D1 round trip per gated request, at most two rows read, zero written on the steady path.

Three decisions the owner still has to make:

1. **Paid plan, and therefore passwords.** The Free plan's 10 ms CPU cannot hold an OWASP-compliant hash (production caps PBKDF2 at 100,000 iterations; confirmed open on workerd #1346 with no timeline). Either the lab runs on Paid ($5 a month, Argon2id at about 20 ms) or it offers passkeys, magic links and Google only. This decides whether email+password is in slice B at all.
2. **The email sender.** Cloudflare Email Service sends natively from a Worker binding since 16 Apr 2026, but it is still beta, Paid-only and quota-ramped for new accounts. Pick it or a third party (Resend, Postmark, SES); either way the sender is a port, so the choice is reversible. This decides what the first process (sign-up verification) talks to.
3. **Sliding idle window, or absolute only.** An idle window that extends on activity needs a throttled write outside the gate and a second timestamp; absolute-only sessions (sign in again after N hours) keep the gate read-only and the schema simpler. OWASP wants both for high-value apps. This decides the `sessions` schema before slice A writes it.

Not a decision yet: a separate auth Worker. It earns its keep only when a second consumer Worker appears, when sessions must live in a different database or jurisdiction, or when a Durable Object becomes the session write authority (adapter-cloudflare 7.x cannot export one from the SvelteKit Worker). None of those is true in slice A.

## 1. Where authentication runs

The api's gate should interpret the credential (option a), and the one fact that decides it is simple: a service binding forwards the browser's `Request` whole, cookies and `Origin` included, in-process and with no network hop. The BFF therefore needs no authority of its own; it forwards. Option b (the BFF decides, the api trusts a header) works only while the api is reachable by binding alone, and the provider CLI is already the second consumer that breaks it. Option d, a separate auth Worker, is a deployment decision, not a modelling one; the section below says when it earns its keep.

| Criterion | a. api gate | b. BFF gate | c. both | d. auth Worker |
| --- | --- | --- | --- | --- |
| One authority for identity | yes | only while the api is binding-only | no | yes (identity only) |
| How the actor reaches an operation | Hono context, set by the gate | `event.locals` → trusted header | duplicated | RPC `Result` → caller's context |
| Where CSRF is checked | api (cookie is forwarded) | BFF | both | BFF (api sees a non-ambient credential) |
| Provider CLI | reuses the gate with a token file | must re-implement the gate | — | reuses `verify` |
| Public api hostname later | fine (csrf + bearer) | breaks the trusted header | — | fine |
| D1 round trips per page load | 2 | 2 | 3 | 2 (lookup) / 1 (signed assertion) |
| Auth store down | every entry refuses | every entry refuses | every entry refuses | lookup: all refuse; assertion: only sign-in refuses |
| OpenAPI | one document | one | one | a second contract (RPC interface + contract test) |
| Local dev | 2 Workers | 2 | 2 | 3 Workers under one `wrangler dev -c` or Vite `auxiliaryWorkers` |

**CSRF follows the credential, not the network.** The api needs CSRF protection exactly when it accepts a cookie as a credential, binding-only or not. If the BFF forwards the browser's cookie (a), a cross-site form POST to the BFF is a CSRF against the api, so either SvelteKit's origin check (form content types, POST/PUT/PATCH/DELETE, production only) or Hono's `csrf()` (checks `Origin` or `Sec-Fetch-Site`, same scope) must run; Hono's works unchanged behind a binding because the headers arrive intact. If the BFF converts the cookie into a header or RPC argument (b, d), the api receives nothing a browser could have attached and needs no check. A bearer token from the CLI is never ambient and needs none either. Hono 4.13.16 (1 Nov 2026) is a security release for `csrf()`.

**Cookie scope.** Cookies are scoped by registrable domain, not by Worker. A `__Host-` session cookie (the right choice: no `Domain`, `Path=/`, `Secure`) is locked to the BFF's hostname, which is exactly right when the api is only reached by binding. If the api ever gets a sibling hostname, SvelteKit's server `fetch` does not forward a cookie to a sibling subdomain; `handleFetch` has to copy it, or better, send it as a bearer header. Different zones would force `SameSite=None` and are the wrong design for a BFF.

**When a separate auth Worker (d) earns its separation on Cloudflare.** When more than one consumer Worker needs the same gate and you want its code and D1 binding in one deployable; when sessions should live in a different D1 database or a Durable Object from business data (jurisdictions, backup cadence); when credentials code wants its own deploy cadence and blast radius; or when Cloudflare Access fronts admin and one place must validate `Cf-Access-Jwt-Assertion`. What it costs: identity keeps one authority but the Worker must stay at `issue / verify / revoke` and never grow role checks; an RPC-only surface has no OpenAPI document, so the address-and-check rule needs a TypeScript interface plus a contract test; each `verify` is a D1 read unless the assertion is self-verifying (then revocation lags by the assertion's TTL); and local dev becomes three configs under one `wrangler dev` (only the primary is exposed on `:8787`). One concrete pull toward d: `@sveltejs/adapter-cloudflare` 7.x says Durable Object and Workflow classes cannot be exported from the SvelteKit Worker, so a DO-backed session store would need its own Worker anyway.

**Environment facts that frame everything** (as of 5 Nov 2026): Hono stable 4.13.16, 5.0.0-rc.1 since 10 Oct; the svelte.dev docs now describe SvelteKit 3.x, where adapter-cloudflare 8.0.x removes `event.platform` in favour of `import { env } from 'cloudflare:workers'` and `csrf.checkOrigin` gives way to `csrf.trustedOrigins`; the lab's 2.x/adapter 7.x line keeps `event.platform.env`. Wrangler 4 multi-Worker dev is `wrangler dev -c primary.jsonc -c other.jsonc`; the old `--x-*` experimental flags are gone. `ctx.access` from Cloudflare Access is not propagated over service bindings or RPC, so Access can only ever gate the public hostname.

**Round trips the budget test asserts** (D1 or DO hops; binding hops are free):

| Chain | a | b | c | d lookup | d signed |
| --- | --- | --- | --- | --- | --- |
| Page load: actor + one business read | 2 | 2 | 3 | 2 | 1 |
| api call from the browser via the BFF | 2 | 2 | 3 | 2 | 1 |
| Provider CLI operation | 2 | re-implements | — | 2 | 2 |

D1 read replication (still beta, docs updated 10 Aug 2026) adds a wrinkle: a sign-out written to the primary must not be read back stale, so the gate's lookup should run `first-primary` or carry the session bookmark; replication is a later optimisation for read-mostly business queries, not for the gate.

## 2. Session storage on Cloudflare

A D1 `sessions` table is the right store at both scales, and it costs about $0 a month at a few hundred thousand users because reads stay inside the 25 billion rows the Paid plan includes. Every alternative either cannot revoke (KV, a stateless cookie) or buys consistency D1 already has at higher cost and worse geography (Durable Objects). Scale A below is 300 users, about 20k gated requests a day; scale B is 300k users, about 20M a day; costs are incremental to the $5 Workers Paid plan, from the pricing pages as read on 5 Nov 2026.

| Criterion | D1 table | Workers KV | DO per user | One coordinator DO | Signed stateless cookie | Short cookie + D1 re-mint |
| --- | --- | --- | --- | --- | --- | --- |
| Consistency | strong on the primary | eventual, up to 60 s or more; negative lookups cached too | strong, single-threaded | strong | none to keep | bounded by cookie TTL |
| Immediate sign-out / disable | yes, one statement | no | yes, inside the object | yes | no | within TTL |
| Read latency | one hop to the primary's region | hot: edge; cold: central | one hop to the user's home colo, placed at first sign-in, never moves | one colo for the planet | zero | zero steady, one per TTL |
| TTL | `expires_at` column + cron sweep | native `expirationTtl` | one alarm per object | one alarm | `exp` claim | `exp` claim |
| Cost, scale A | $0 | $0 | $0 to $5 | $0 | $0 | $0 |
| Cost, scale B per month | about $0 | about $440 | about $90 plus $1.7k to $9k duration | about $90; peaks near the 1,000 req/s per-object limit | $0 | about $0 |
| Budget test asserts | 1 round trip, at most 2 rows read, 0 written | 1 KV read | 1 DO request | 1 DO request | 0 | 0 steady, 1 per TTL |
| Store down | all refuse | all refuse; stale cache can mask it | that user refuses | all refuse | cannot fail, cannot revoke | fail-open within TTL is a choice |

**D1, the provisional choice, holds.** Without the Sessions API every query goes to one primary, so reads see writes. Keep replication off for the gate's lookup, or run it `first-primary`; the disable-user case has no shared bookmark between the admin's write and the victim's next request, so only the primary gives it immediate effect. Rows read count scanned rows, so the lookup must be an indexed point read (primary key on the id, index on `user_id` for the disable fan-out), and the session row should join the user row in one statement. The one cost trap is writing on every request: touching `last_seen_at` each time is about 600M writes a month at scale B (about $550); refreshing the sliding window only when it is older than, say, 15 minutes is about 30M, inside the 50M included. That is a design rule worth writing down: the gate reads, and writes only when the window needs extending. D1 returns `meta.rows_read` and `meta.rows_written` on every query, so the budget test asserts them directly without a mock. Since 11 Sep 2025 D1 retries read-only queries twice on retryable errors.

**KV is a cache, not an authority.** The docs are explicit: eventually consistent, usually immediate in the writing colo, up to 60 seconds or more elsewhere, and a cached "not found" delays visibility further. Sign-out and disable are deletes, so a revoked session keeps authenticating anywhere the old value is cached. It also bills every read, cache hits included, at roughly 500 times D1's per-row read price, and allows one write per second per key. It violates "stores report facts" by design: the fact may be a minute old.

**A Durable Object per user is an anti-pattern for the gate** and a reasonable authority for session mutations. For the read path: every request routes to the object's home colo, placed at the user's first sign-in and never relocated, so travelling users pay a cross-region hop on every call; duration is billed while the object stays awake (about 10 s after each request), which is where the $1.7k–9k range at scale B comes from, depending on how bursty traffic is; the first request after idle re-runs the constructor on the hot path; and single-threaded execution serialises an idempotent read for no benefit. Where it fits: issuing, revoking one, revoking all, and concurrent-session limits, the write-ordering problems the KV docs themselves say to solve with a DO. A per-session object is strictly worse, since "disable user" then needs an index elsewhere. One coordinator object is fine at scale A and wrong at scale B (one colo for everyone, \~230 req/s average with peaks at the per-object limit). SQLite-backed DOs went GA on 7 Apr 2025 with a free tier; storage billing began 7 Jan 2026.

**A stateless signed cookie cannot be ended**, which contradicts the two requirements already written (sign-out ends the row, disable ends all rows) and OWASP's rule that logout invalidates server-side. If it is ever used, a plain HMAC-SHA-256 over `session_id|user_id|exp` with no parsed algorithm, never a JWT, for a first-party cookie.

**The one hybrid worth keeping in reserve**: a short-lived HMAC cookie (about 5 minutes) carrying `session_id`, `user_id`, `minted_at`; the gate skips D1 while the cookie is fresh and re-reads and re-mints when it is not. Steady-state store reads become zero, revocation lags by at most the TTL, and one operation still owns the decision. This is the first move if latency for users far from the primary ever fails its test, not KV and not DOs.

**Session id and cookie, per OWASP and rfc6265bis-22 (Dec 2025).** 256 bits from `crypto.getRandomValues`, base64url; store only a SHA-256 of it so a database dump cannot be replayed. Rotate on sign-in and on any privilege change, destroy the old id, never accept an id the server did not issue. Idle and absolute timeouts enforced server-side; for a bookkeeping product the high-value end of OWASP's examples (short idle, 4–8 h absolute) is the honest choice. Cookie: `__Host-sid=…; Secure; HttpOnly; SameSite=Lax; Path=/`, no `Domain`. `Clear-Site-Data` on sign-out; `Cache-Control: no-store` on sensitive replies. A CLI token is a separate opaque token in the same table with a `kind` column and the same revocation path.

Rob's primary belongs in `wnam`; a same-region hop is single-digit to low-tens of milliseconds and a trans-Atlantic one adds roughly 80–120 ms (planning figures, not from a Cloudflare page).

## 3. Identity methods and their libraries

The lightweight-library tier this design would have reached for no longer exists: Lucia was deprecated in March 2025, Arctic and the `@oslojs/*` packages on 29 Jul 2026, all by their author, who now publishes single-file replacement code and the Auth Book instead; Auth.js was folded into Better Auth on 22 Sep 2025 and receives security patches only; Better Auth became a Vercel company on 7 Jul 2026. The field has consolidated onto Better Auth as the framework and copy-the-primitives as the alternative, and for a design where the api owns the decision, copy-the-primitives is the better fit. The one library worth adopting outright is `@simplewebauthn/server`.

**Password hashing is the real platform constraint.** The Free plan allows 10 ms CPU per request, Paid 30 s by default (raisable to 5 min). Production Workers cap WebCrypto PBKDF2 at 100,000 iterations (workerd issue #1346; the open-source runtime no longer enforces it, so `wrangler dev` runs 600,000 without error and local tests will not catch it), while OWASP's floor for PBKDF2-SHA256 is 600,000. `node:crypto` exposes `pbkdf2` and `scrypt` but not `argon2`. Measured on 5 Nov 2026 in local workerd (wall time, 2 vCPU, best of three): PBKDF2 100k 12 ms; scrypt at Better Auth's default 52 ms, at OWASP's N=2^17 230 ms; pure-JS Argon2id (`@noble/hashes`) 142 ms; `hash-wasm` fails outright ("Wasm code generation disallowed by embedder", because it compiles base64-embedded WASM at runtime); `@phi-ag/argon2` with the `.wasm` imported as a module 21 ms at OWASP's m=19456 t=2 p=1, 19 ms at 12288/3/1, 26 ms at 47104/1/1.

Recommendation: Paid plan, Argon2id via `@phi-ag/argon2` at m=19456 KiB, t=2, p=1, pepper by HMAC-SHA256 from a Workers secret before hashing, PHC strings stored with their parameters, re-hash on sign-in when parameters change. The package's `tryHash` / `tryVerify` return `{ success, error }`, which is errors as values. The hashing lives in the `auth` area's credential store, which reports verified, not verified, or needs-rehash, and the operation decides. On the Free plan nothing OWASP-compliant fits in 10 ms; the honest option is to not offer passwords there (passkeys, magic links and Google only). Caveat: these are wall-clock figures in local workerd; production CPU metering is opaque, and a community template reports Better Auth on Pages hitting CPU limits, solved by a separate hasher Worker over a service binding.

## 5. Threats and where each answer lives

Thirteen threats, and the answer to each has one home in the chain. Three facts verified in this pass change earlier assumptions: Hono 4.13.16's `csrf()` fix closes a Chromium `<a ping>` bypass, the third bypass of that middleware, so a content-type allow-list is a brittle primitive that needs a second check; `Clear-Site-Data` is blocked in Chromium since April 2025 (Firefox 138+ and Safari 17+ honour it), so it is a courtesy and server-side invalidation is the control; and `workers.dev` and `pages.dev` are on the Public Suffix List, so two Workers on `*.workers.dev` are cross-site to each other, which isolates them and also kills any plan where the browser talks to both hosts. ASVS ids are 5.0.

The CSRF row is the one place the gate's two-things contract is under pressure: the check is not about who the actor is but whether the credential channel can be trusted for this request, so it belongs in a named stage ahead of the gate (section 6 takes this up). And the Rate Limiting binding is a cost shield, not a correctness control; the per-account counter in D1 is the control, and a proxy network defeats any per-colo IP ceiling.

## 6. Where the provisional decisions are wrong

None of the five is overturned; three are amended in ways that matter, and the amendments are the real output of this research. The pattern across them is the same: each decision was stated as "once" when the mechanism is actually two things, and naming the second thing is what keeps the story honest.

**0.1 Authentication as a gate, authorization never in the gate: amend.** The strongest case against is that "exactly two things" is already false once CSRF exists. A gate that reads a cookie must decide, per request, whether this cookie may be trusted at all, and OWASP treats origin verification as a mandatory part of trusting a cookie on an unsafe method. Left implicit, nobody owns the content-type allow-list, which is exactly how Hono's three `csrf()` bypasses happened. The fix is not a new abstraction: the origin and content-type check is itself a gate by the definition (it refuses in the envelope and attaches nothing, like the body limit), so the ordered list grows by one, `requestId`, `bodyLimit`, `channel`, `authenticate`, and each gate keeps its two-things contract. Second, an anonymous-admitting gate is default-allow unless the runner is default-deny: an operation with no row in `access.md` must fail generation, not run for anonymous. Third, "applied once by a shared runner" is true for the role column and false for ownership, which cannot be known until the id is parsed and the row located; the role check runs before validation (and gives 403-before-400 for free), the scope is handed to the operation and enforced by the store, and the story should say two mechanisms. Last, refusing a bad cookie is the wrong default: a user who signs out in one tab and submits a form from another 200 ms later would see an error envelope instead of the sign-in page. An unknown or unparseable cookie becomes `anonymous` with a clear-cookie hint for the BFF; an unknown bearer token from the CLI is refused with 401, because the client asserted a credential and it is wrong; a live session for a disabled user is refused with `account_disabled`.

**0.2 Server-side sessions in D1, `__Host-` cookie set by the BFF: keep, amend the minting.** The decision never said who mints or how the raw id crosses the binding. If the api writes `Set-Cookie` and the BFF forwards the response, the cookie works (the browser scopes it to the BFF host) but the api now knows cookie names and attributes, and a CLI calling the same operation receives a `Set-Cookie` it must ignore. So `sessions.start` returns `{ token, expiresAt }` in the result envelope; the BFF delivery turns it into the cookie and the CLI into a keyring entry. The raw token lives in memory in two Workers for one request and at rest only as a SHA-256 (fast hashing is enough for 256 bits of entropy). Three more conditions: a `channel` column (`cookie` or `bearer`) with its own idle and absolute rules, and a bearer token never accepted from a `Cookie` header or the reverse; the gate's read runs on the primary (a replica with `first-unconstrained` can be arbitrarily stale, so a revoked session would read as live); the sliding idle window is extended at most once per N minutes and outside the gate, after the operation, via `waitUntil`, so the gate reads and never writes. And `workers_dev = false` in the api's config, since a dashboard-only disable comes back on the next deploy.

**0.3 `users` and `auth` as two areas, `auth` may read `users`: amend the layering rule.** The cycle appears immediately. Sign-up creates a user (a `users` authority) and then a credential and a verification (`auth`), so "auth may read users" must mean "auth may call users operations", and if `auth` wrote the `users` table through its own store there would be two authorities for user rows. Worse, `users.disable` is a users decision whose required effect, ending every session (ASVS 7.4.2), is an auth write that `users` may not reach. The resolution is already in the story's chain: a process is the stage above operations, and a process may compose operations from several areas while areas never import each other. `signUp` and `disableUser` are processes. For correctness independent of step ordering, the gate's session lookup joins `users.disabled` in the one statement it already makes, so a disabled user is refused even if the row-ending step lagged or failed: the join is the control, ending the rows is hygiene. That also answers where `disabled` is enforced (the gate) and where `role` lives (`users`; it is a fact about the person, read by `auth` when it builds the actor). OAuth account links belong in `auth`, keyed on provider and `sub`; `email_verified_at` is a `users` fact written by the `verifyEmail` process after `auth.consumeVerification` succeeds, one more process that spans both.

**0.4 Ownership by the scoped query, wrong owner reads as `not_found`: keep, with two conditions.** The case against: a `WHERE user_id = ?` baked into the store is a decision; admin reads need a different query; the first shared resource (a team, a client's project) makes `user_id` the wrong fact; and `not_found` for an existing row can collide with real 404 handling in the BFF. It holds because the operation makes the decision when it chooses the scope it hands the store, `{ ownerId }`, `{ any: true }` for admin, later `{ memberOf }`; the store reports "no row for this scope" and the operation names it `not_found`. Timing is uniform because the query shape is identical for missing and foreign rows, and list endpoints scoped the same way cannot enumerate. OWASP has no 403-versus-404 rule, so `not_found` is legitimate; the one case it must not cover is "yours but refused by state", which is `forbidden` with a reason. Conditions: writes are scoped too (`UPDATE … WHERE id = ? AND user_id = ?` returning the change count, never read-then-write), and the scope is a typed input the operation passes, with no default scope in the store, which keeps default-deny.

**0.5 `access.md` as a static operation × role × owns table: amend the columns.** A static table can say who may attempt an operation; it cannot carry state-dependent conditions (verified email, a locked resource, an expired trial) or relationships beyond ownership without growing columns forever or lying by omission (ASVS 8.1.2 expects documented rules that depend on state). The columns become `requires` in {anonymous, member, verified\_member, admin}, an actor precondition the runner applies before validation, and `scope` in {own, any, n/a}, handed to the operation as the store scope. `verified_member` earns a place because it is an actor fact from the gate's join, not a resource fact. Anything state-dependent is declared in the operation's own use case, enforced in the body after the row is loaded, and returns `forbidden` with a reason. What the check can verify: statically, every operation has exactly one row, every row names a real operation, cells use the closed vocabulary, and the generated `access.ts` matches the table; dynamically and cheaply, each operation called as each actor kind with an empty body asserts the runner's verdict (401, 403, or "reached validation"), which is the budget-test style applied to access. What it cannot verify is that `own` is enforced, since that lives in the store scope; that needs a second check, a lint that every query against an owned table takes a scope parameter.

CSRF semantics in 3.x, from `runtime/server/csrf.js`: skipped in dev; forbidden when the method is POST, PUT, PATCH or DELETE and the `Content-Type` is missing or a form type (`application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`) and `Origin` differs from `paths.origin || url.origin` and is not in `trustedOrigins`; 403 with SvelteKit's own text. JSON mutations to `+server` endpoints are not covered, which is why the api keeps its own `channel` gate.

Implications: the BFF forwards the browser request with `env.API.fetch(event.request)`, headers intact; `cookies.set('__Host-sid', token)` needs no options in production, and under `http://localhost` the browser refuses the prefix (use an unprefixed name under `DEV` or https in dev); `handleError` is where the BFF translates api failures and framework 404/405/413 into its own copy; remote functions stay off so no mutation bypasses page → form action → api; `compatibility_flags: ['nodejs_als']` is required.
