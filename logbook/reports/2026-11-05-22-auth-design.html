Authentication design
    workers-hono-svelte lab · before slice A

    Authentication design

    The api is the one authority for "who is this". Four gates run in order before routing. authenticate turns a hashed cookie or bearer token into an Actor with one D1 statement and no writes. Sessions live in D1 with a 24 h idle and 30 d absolute timeout. Authorization is never a gate: a runner applies requires from access.md, and stores apply scope. Every identity method converges on sessions.start. Thirteen threats each have a home in the chain.

    For Rob and his coding agent. Everything here is decided unless marked open. Terms are used exactly as in the brief.

    0The system in one paragraph

    A pnpm monorepo on Cloudflare. apps/api is a Hono Worker: a JSON api with an OpenAPI document generated from a spec. apps/bff is a SvelteKit Worker (Svelte 5.57.3, SvelteKit 3.1.0, adapter-cloudflare 8.x: bindings come from import { env, ctx } from 'cloudflare:workers', not event.platform). It renders pages and calls the api over a service binding: in-process, no network hop, the browser Request forwarded whole. D1 is the database. A CLI delivery is designed: a consumer over fetch, or a provider running operations in-process.

    Design rules everything honours

    • Every business decision has one authority, an operation.
    • Stores report facts; operations decide.
    • Errors are returned values (Result), never thrown across a boundary.
    • Every spec level has an address (file + id) and a check (a test or generator that fails on drift).
    • Performance is a design input, and a number a cheap test asserts.

    Why channel is its own gate

    OWASP treats origin verification as mandatory before trusting a cookie on an unsafe method. Hono's csrf() has had three bypasses: CVE-2024-43787 (uppercase content-type), and 4.13.16 fixed Chromium <a ping> POSTs. A content-type allow-list alone is brittle. A bearer token (CLI) is never ambient and needs no CSRF check.

    Binding and unit

    Each gate has a binding in the delivery: Hono middleware in apps/api/src/gates/*.ts, or a token-file reader in a provider CLI. When it has a decision over a port, it also has a unit in packages/gates. Construct lists the bindings in order; that list is the gates' address, as the route table is the routes'. No Gate interface, no registry: two plain functions per gate with a port is a convention, held by tests.

    Token and cookie

    • 32 bytes from crypto.getRandomValues, base64url. Minted by the operation sessions.start, which returns { token, expiresAt } in the result envelope.
    • Each delivery stores it its own way. The BFF sets __Host-sid=…; Secure; HttpOnly; SameSite=Lax; Path=/, with no Domain, locked to the BFF host. The CLI writes it to its keyring or config.
    • The api never writes Set-Cookie. A bearer token is never accepted from a Cookie header, and vice versa: the channel column and the channel gate agree.

    Timeouts, rotation, ending

    • Both timeouts are business constants: idle 24 h (sliding), absolute 30 d. CLI bearer tokens: no idle, longer absolute.
    • Idle refresh: when idle_until − now < idle/2, the binding schedules sessions.touch after the response. At most one write per session per 12 h.
    • Rotation: a new row on every sign-in and re-authentication; the old row ended. Ids are server-minted only, so classic fixation is impossible.
    • Sign-out: this device ends one row; all devices ends every row for the user and requires re-authentication. The BFF sends an expiring Set-Cookie and Clear-Site-Data as a courtesy. Chromium has blocked it since Apr 2025; the row is the control.
    • Disable user: users.disable is a process. It sets users.disabled and ends all sessions (hygiene). The gate's join on users.disabled is the control, so a disabled user is refused even if row-ending lagged.
    • Read replication: keep it off for the gate (or first-primary). A replica read can be arbitrarily stale and would show a revoked session as live.

    Isolation: what it buys, per pillar

    Isolating the session store does not move the first hop. A service binding or RPC call is in-process, so a separate auth Worker adds no latency and removes none; a Durable Object per user or Workers KV changes the geography for the worse or the correctness for the worse. What isolation buys is security: credentials and the pepper in a store business code cannot bind. Reliability is slightly worse (one more thing that must be up, both fail closed). The sessions port is the seam: construct decides whether it is answered by a D1 store, a second binding, or an RPC client, and neither the unit nor the gate changes.

    Two databases, one key

    The area boundary is physical. The identity database holds users, credentials, sessions and verifications. The app database holds business rows (todos) that carry a user_id as an opaque value. The api binds both (IDENTITY_DB, APP_DB); the stores under packages/data split the same way; migrations and the data spec are per database.

    • The user id is the only foreign key between the two. Minted once by the id source in users.create, opaque and immutable; never the email, which can change. The database never enforces it.
    • No query joins across databases. The gate joins sessions to users inside identity. Todo operations are scoped by the actor's user_id inside app and never look at users: the gate already proved the user exists and is enabled. Sign-in, sign-out, rotation, verification, password change, admin list and disable: identity only.
    • Reads that need both sides are composed by id in code, never by SQL. An admin page that wants todo counts per user calls GET /users and a counts endpoint and merges on user_id; that is the BFF composition rule (a view names the endpoints it reads). Lookups use WHERE user_id IN (…), batched by 100 (D1's bound-parameter limit).
    • Referential integrity is a process concern. Deleting an account removes app rows in one database and the user in the other: two transactions, no atomicity between them, exactly what the step record is for. Sign-up stays atomic because everything it writes is in identity.
    • Per pillar. Security: all PII and every credential hash in one database business code never binds; a leak of the app database names nobody. Performance: the gate is still one round trip, and the app database can turn on read replicas later while identity stays primary-only. Maintainability: the identity half knows nothing about todos and is the reusable package. Reliability: a request needs two databases up instead of one, both fail closed.
    • Not shared across products. One identity database per product. Sharing one is single sign-on by another name; the reusable part is the package, not the data.

    6Authorization, never a gate

    How it is enforced

    • A shared runner in the operations layer applies requires before the body. It is an actor fact, so it gives 403-before-400.
    • The operation passes a typed scope to the store: { ownerId }, { any: true } for admin, later { memberOf }. The store has no default scope.
    • Writes are scoped too: UPDATE … WHERE id = ? AND user_id = ? returning the change count, never read-then-write.
    • Wrong owner → not_found. "Yours but refused by state" → forbidden with a reason. State conditions (locked, trial expired) are declared in the use case and enforced in the operation body after the row loads.
    • Static checks: every operation has one row, every row names a real operation, the generated file matches the table. Dynamic check: each operation called as anonymous, member and admin with an empty body asserts the runner's verdict.
    • What the checks cannot verify: own, which lives in the store scope.
    • A delivery may mirror requires for ordering or OpenAPI security, but never decides.

    GGlossary

    gate
    Runs once per entry, before routing, for every request. Attaches a fact to the request or refuses in the error envelope.
    binding
    A gate's delivery part: Hono middleware in apps/api/src/gates/*.ts, or a token-file reader in a provider CLI. Construct lists bindings in order.
    unit
    A gate's decision over a port, in packages/gates. Today only authenticate has one. Also the thing an entry point calls: an operation or a process.
    actor
    Who the request acts for: anonymous, Actor { userId, role, emailVerified }, or a system actor { kind: 'system', source }. A business type operations receive.
    credential
    What a request presents: the __Host-sid cookie or a bearer token. In the auth area, a credentials row (password, passkey, oauth).
    channel
    How the credential arrived: cookie | bearer | none. Attached by the channel gate; matches sessions.channel.
    scope
    The typed limit an operation passes to a store: { ownerId }, { any: true }, later { memberOf }. Declared per operation in access.md as own, any or n/a.
    process
    A multi-step unit that composes operations, possibly across areas. Immediate today, durable (Cloudflare Workflows) later. Records steps.
    step record
    Step<T> = { name, attempt, started, finished, result }, written per process step.
