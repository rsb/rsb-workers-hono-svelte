- **SvelteKit 3.1.0 and adapter-cloudflare 8.x are what the BFF runs

  research was first read against 2.x; a follow-up (section "SvelteKit

    `env.API.fetch(event.request)` with
    `import { env, ctx } from 'cloudflare:workers'`; the `Request` goes
    to the binding whole, so `Cookie`, `Origin` and `Sec-Fetch-*`
    survive and no `event.fetch` cookie-forwarding rule applies. Decide

    types (now including a missing `Content-Type`) and only in
    production, and its 403 text is SvelteKit's, not ours. The api's
    `channel` gate stays for exactly those reasons.
  - Cookies: `cookies.set` now defaults to `httpOnly`, `secure`
    (production), `sameSite: 'lax'`, `path: '/'`, which are the
    `__Host-` prerequisites. Under `http://localhost` the browser
    refuses a `__Host-` cookie: use an unprefixed name under `DEV` or
    serve dev over https; say which in the plan.
  - `handleError` now receives every error (`kind: app | framework |
    validation | unknown`) and may return `status` and `message`. It
    is the one funnel where the BFF writes every message the user sees
    (PRD rule); use it, and `error(status, 'message')` everywhere.
  - Remote functions stay off (`experimental.remoteFunctions` unset);
    with the flag off a `*.remote.ts` file is a compile error, so no
    mutation can bypass page → form action → api. Record why.
  - wrangler for the BFF: `compatibility_flags: ['nodejs_als']`,
    wrangler ≥ 4.118.0, Node ≥ 22.17. Durable Object and Workflow
    classes still cannot be exported from the SvelteKit Worker (adapter
    docs, kit#1712 open); they belong to the api Worker.
  - Local dev: the adapter uses wrangler's `getPlatformProxy` behind a
    stubbed `cloudflare:workers` module, not `@cloudflare/vite-plugin`.
    Run `wrangler dev` for the api and `vite dev` for the BFF; the
    `API` binding resolves through Miniflare's dev registry (wrangler
    ≥ 4.154.0 turns it on by default; both must share
    `CLOUDFLARE_DEV_REGISTRY_PATH` if they do not find each other).
    This is the one path the research could not verify end to end;
    prove it first and record the result.
  - `csp.directives['frame-ancestors']` reaches the header on SSR
    pages and is dropped only on prerendered ones; keep auth pages
    SSR'd or set the header in `handle`.

## Decisions (story entries L37 to L43)

Record these in `logbook/the-api-story.md` and the glossary as part of
stage 23, in the form the ledger uses. The wording below is the
decision; the chapter text is the agent's.

- **L37, gates are a stage.** The chain is startup → gates → entry
  point → [process] → operation → port ← data. A gate runs once per
  entry, before routing, for every request, and does exactly two
  things: attach a fact to the request, or refuse in the error
  envelope. It never reads business data for a business purpose and
  never decides what a request means. A gate has a *binding* in the
  delivery (Hono middleware in `apps/api/src/gates/`, a token reader in
  a provider CLI) and, when it has a decision over a port, a *unit* in
  `packages/gates`. Construct lists the bindings in order; that list is
  the gates' address, as the route table is the routes'. No `Gate`
  interface and no registry: two plain functions per gate are a
  convention, held by tests. Import rule: `gates` imports `business`
  and `fail` only; `gates` never imports `operations`, `valid` or
  `data`; `operations` and `data` never import `gates`.
- **L38, the gates of the api, in order.** `requestId` (mints the id,
  binds the request-scoped logger; binding only), `bodyLimit` (413
  before parse; binding only), `channel` (for cookie-bearing unsafe
  requests: `Sec-Fetch-Site` in {same-origin, none} with `Origin` equal
  to the BFF origin as fallback, refusing when both are absent; JSON
  endpoints accept only `application/json`; attaches `channel: cookie |
  bearer | none`; binding only), `authenticate` (binding + unit). The
  BFF runs no gate; it forwards the browser request over the service
  binding and decides nothing. A consumer CLI attaches
  `Authorization: Bearer`; a provider CLI runs the same unit.
- **L39, authentication is a gate, authorization never is.** The unit
  `authenticate({ credential, now }, { sessions })` returns
  `Result<Actor, Unauthenticated | AccountDisabled>` plus
  `refreshDue`. No credential → `anonymous`. Unknown, expired or
  unparseable *cookie* → `anonymous` with a `clearCookie` hint (the
  sign-out race between two tabs ends at the sign-in page, not an
  error). Unknown *bearer* → refuse 401. Live row for a disabled user →
  refuse `account_disabled`. The unit never writes. Authorization is
  declared once in `prd/todo/access.md`, generated once into a
  property on each operation, applied once by a shared runner in the
  operations layer before the body, and at most mirrored by a delivery
  for ordering or OpenAPI `security`.
- **L40, sessions are rows in D1.** Table `sessions`: `id`,
  `token_hash` (SHA-256 of a 256-bit random token; the raw token is
  never stored), `user_id` (indexed), `channel`, `created_at`,
  `idle_until`, `expires_at`, `ended_at`, `ended_reason`. Both timeouts,
  as business constants: idle 24 h sliding, absolute 30 d; bearer
  tokens have no idle window and a longer absolute one. `sessions.start`
  returns `{ token, expiresAt }` in the envelope and each delivery
  stores it its own way: the BFF as
  `__Host-sid=…; Secure; HttpOnly; SameSite=Lax; Path=/`, the CLI in its
  config. The api never writes `Set-Cookie`. A bearer token is never
  accepted from a `Cookie` header, nor the reverse. The gate's lookup
  is one statement, `sessions JOIN users`, on the primary, never a
  replica. The gate reads; when `refreshDue` is true the binding
  schedules `sessions.touch` through `ctx.waitUntil` after the
  response, at most once per session per half window. Rotation: a new
  row on every sign-in; the old row ended. Sign-out ends one row; all
  devices ends every row for the user. Why not KV, a Durable Object or
  a stateless cookie: the research's section 2.
- **L41, `users` and `auth` are areas; processes cross them.** `users`
  owns the person (`users`: `id`, `email`, `name`, `role`, `disabled`,
  `email_verified_at`, `created_at`). `auth` owns proof and continuity
  (`credentials`, `sessions`, `verifications`). Areas never import each
  other; `auth` builds the actor from a `users` row through the gate's
  join. Anything that writes to both is a process: `signUp`,
  `disableUser`, `verifyEmail`, `changePassword`. The gate's join on
  `users.disabled` is the control for a disabled user; ending the rows
  is hygiene.
- **L42, two D1 databases.** The identity database holds the `users`
  and `auth` tables; the app database holds business rows that carry a
  `user_id` as an opaque value. The api binds both (`IDENTITY_DB`,
  `APP_DB`); `packages/data` splits the same way; migrations and the
  data spec are per database. The user id is the only foreign key
  between them, minted once by the id source in `users.create`, never
  the email, never enforced by the database. No query joins across
  databases; a read that needs both sides is composed by id in code
  (`WHERE user_id IN (…)`, batched by 100, D1's bound-parameter limit).
  Referential integrity across the two is a process concern. One
  identity database per product.
- **L43, ownership is a scope the operation passes.** The operation
  hands the store a typed scope (`{ ownerId }`, `{ any: true }` for
  admin, later `{ memberOf }`); the store has no default scope; reads
  and writes are scoped alike (`UPDATE … WHERE id = ? AND user_id = ?`
  returning the change count, never read-then-write). No row in scope
  is reported as a fact and the operation names it `not_found`;
  "yours but refused by state" is `forbidden` with a reason.
  `access.md` has two columns per operation: `requires` in {anonymous,
  member, verified_member, admin} and `scope` in {own, any, n/a}; a
  missing row fails generation.

Glossary terms to add: gate, binding, unit (of a gate), actor,
credential, channel, scope, process (amend: may compose operations
across areas), step record, identity database, app database.

## The pillars and the analytics loop (one small item)

The owner's pillars are Reliability, Security, Performance and
Maintainability. They are documented once and measured; nothing is
tagged with them and no new build rule comes from them.

- `logbook/pillars.md`: one paragraph per pillar, what it means in this
  system and which signal we read for it. The signals come from outputs
  the lab already produces: the budgets tests (performance), the
  `check:join`, `check:api` and `check:rules` reports (drift,
  maintainability), vitest's JSON report by level and the construct
  tests that exercise failure modes (reliability), the threats table's
  coverage (security).
- `logbook/threats.md`: a table of threat, mitigation, source (OWASP
  cheat sheet or ASVS 5.0 id), home in the chain, and the test that
  exercises it; the last column may be empty. Seed it with the thirteen
  rows in the explainer's section 9. It is a document that the
  security number is counted from, never a spec with a join check.
- `tooling/pillars/`: one script that reads those outputs and renders
  `logbook/pillars-view.md`; run at the end of each stage; read before
  deciding the next. Keep it small.

## Two research corrections the agent needs

- Hono's `csrf()` checks `Origin` or `Sec-Fetch-Site` for form content
  types only and has had three bypasses (CVE-2024-43787; 4.13.16 fixed
  Chromium `<a ping>` POSTs). The `channel` gate is ours, not the
  middleware; it refuses when both headers are absent on an unsafe
  method.
- Production Workers cap WebCrypto PBKDF2 at 100,000 iterations and
  local `wrangler dev` does not enforce the cap, so a local test cannot
  catch it. Slice B hashes with Argon2id via `@phi-ag/argon2` with the
  `.wasm` imported as a module (`hash-wasm` fails on workerd). Nothing
  in slice A hashes a password; the seeded dev session has no
  credential.

## Slice A: ownership without login

The goal: every todo belongs to a user, and every request carries an
actor, before any sign-in exists. The actor comes from a seeded session
row, so the real gate path runs from the first stage and nothing in the
gate learns about environments.

What slice A builds:
1. `packages/gates` with `authenticate`, its unit test (fixed `now`,
   fake `sessions` reader, every branch of L39), and the dependency
   rule in the existing check.
2. The four gate bindings in `apps/api/src/gates/`, listed in order in
   construct; `requestId` binds the `log` port (backlog D) and
   `serverFailure` logs through it, one JSON line
   `{ requestId, method, path, kind, message, chain }`.
3. The identity database: migrations for `users` and `sessions` (the
   `credentials` and `verifications` tables wait for B and C); a seed
   for local dev with one member and one admin, each with a live
   session whose raw token is in `.dev.vars` (never in
   `wrangler.jsonc`, rl-0012); the `IDENTITY_DB` binding; the stores
   under `packages/data/d1/identity/`. The app database keeps todos,
   with `user_id` added and every store method taking a scope (L43).
4. `prd/todo/access.md`, `tooling/access/` generating
   `packages/business/src/access.ts`, the runner in `operations`, and
   the two checks: static (one row per operation, every row names a
   real operation, generated file matches) and dynamic (each operation
   called as anonymous, member and admin with an empty body asserts the
   runner's verdict).
5. The seven todo use cases gain `Given: the todo belongs to the actor`
   and the `Applies:`/`Assumes:` lines the join check needs;
   `prd/todo/api.md` gains `security` on each endpoint; `gen:api`.
   The accounts feature documents from stage 22 are the source for
   every state slice A renders; `feature-todos-list.md`'s Who line
   becomes true here. Identity's data cases go in
   `prd/todo/data/identity.md` (L46).
6. The BFF forwards the dev session cookie and renders the shell's
   signed-in state from the api's reply (one call per page load,
   recorded in the BFF budgets).
7. Budgets: gated request = 1 identity round trip, ≤ 2 rows read, 0
   written on the steady path; every todo chain's existing numbers
   unchanged.
8. `tooling/config-check/` (backlog E, first half): reads the config
   schema and checks `.dev.vars` and the CI secrets; `readConfig`
   returns a `Result`. The `unavailable` 503 half waits for the PRD
   deviation.
9. The pillars file, the threats table and the view script.
10. Story: a gates chapter, L37 to L43, the glossary terms, the review
    tour at `logbook/reports/2026-11-05-23-slice-a-review-tour.md`.

Named for later, not built here: B (email/password sign-in and
sign-out, the sessions page, `credentials`, Argon2id, the `channel`
gate's Turnstile verification in the BFF), C (sign-up with email
verification as the first process, the step record (backlog G), the
outbox with Cloudflare Email Service first and Resend second), D
(roles and the admin pages, `disableUser`), E (a second identity
method: passkeys or Google).
