   tell the owner. `git fetch` fails in the sandbox; the owner's pull
   updates `main`.
3. **Present a plan, then ask the owner** before any code. These are
   the questions to settle:
   - **The branch name**, for example `feat/slice-5-delete`.
   - **Naming.** The PRD's slice is "Delete", the route is `DELETE`,
     and the UI says "Remove". Which word do the contract, the
     operation, the port method and the action use?
   - **The reply.** The PRD says `{ id }`. Is it a new contract shape
     (for example `RemovedReply = v.strictObject({ id })`)?
   - **The store fact.** For example, `deleteTodo(id)` returns whether a
     row was deleted, using one `DELETE … WHERE id = ?1 RETURNING id`.
     The operation turns "no row" into `notFound`, as `updateTodo`
     does.
   - **Removing a todo that is already gone.** The API answers 404.
     Does the BFF show "Something went wrong. Try again.", or treat it
     as done, since the reload drops the row either way?
   - **Without JS.** Remove is a plain `?/remove` form post, as toggle
     is, so it can work without JS. Confirm.
   - **With JS, when does the row go?** Either the row goes at once
     (pending, as toggle shows its new value at once) and comes back on
     failure, or the row waits for the reply.
   - **A failed remove.** Where is the message shown? The likely
     place is the row's own error, as for toggle. This follows "each
     form keeps its own failure" (Q8).
   - **Focus after a remove from the keyboard.** The focused button
     goes away with its row. Where does focus go: the next row, the
     previous row, the new-todo input, or nowhere?
   - **Visibility** (deviation 11). The button is always in the DOM.
     It has opacity 0, and opacity 1 on `:hover` or `:focus-within` of
     the row, and always under `@media (hover: none)`. It is not
     rendered while editing (deviation 18, 4.1).
   - **Scenario 5.2, "Given only buy milk".** The e2e database is
     shared, and the earlier files leave todos in it. Files run in
     name order, so a `delete.test.ts` would run second, after
     add-and-list. How is "only" made true? For example:
     - the test removes every todo through the UI first;
     - a delete file that runs first;
     - another way the owner prefers.
4. **Known knock-on: `edit.test.ts`.** `titleOf` finds the title by
   `getByRole("button", { name: title })`, a substring match. The
   remove button's name, "Remove ‘title’", also contains the title, so
   once remove exists `titleOf` matches two buttons. It needs to change.
   This ties to the open decision on the title button's name (tour
   item 11). Then add 4.1's "remove is hidden" check, and drop the
   comment at the top of the file.
5. **Build in layers,** testing each tier:

     construct test's fake store gains the method);
   - BFF `api/todos.ts` and the action;
   - UI;
   - e2e 5.1 and 5.2 in `apps/bff/e2e/delete.test.ts`, plus the 4.1
     check.

   E2e hovers over the row, then clicks the remove button (deviation
   11). It finds the button by its name, "Remove ‘title’".
6. **Run** `pnpm check`, `test:unit`, `test:integration` and
   `test:e2e`, each in a fresh Bash command (see Environment). Then
