## What stage 21 builds

Handoff 12's row C: a budget is the most round trips a unit may make
to the level below it, written as a number, with a cheap-tier test
that fails when the code goes over. It gives L11 ("performance is a
design input", in the story's decisions list, about line 77) the sensor it
lacks: today a second store call in an operation, or a third statement
in a store method, passes every test.

**Today, by level:**

| Level | The unit | What it calls | Counted today? |
|---|---|---|---|
| Data | each `DbStore` method (`packages/data/d1/src/todos.ts:147`) | D1: `all` or `run` on a prepared statement, or one `batch` (`packages/data/d1/src/driver.ts:19,33,54`) | partly: `fakeD1` (`packages/data/d1/test/unit/fake-d1.ts`) records every `prepare` and each batch's size, not the calls that reach D1. Some tests assert `prepared` has length 1, or `batches` is `[2]` |
| Api | each route, from the handler down | the `DbStore`, through the operation's port | no. `apps/api/test/unit/construct.test.ts` has an array-backed `fakeDbStore` (line 17), entered at `constructOperations` |
| BFF | each page load and each form action | the api, through the `API` service binding | partly: `load-todos.test.ts`'s `routed` fake records each URL asked, and `/active` is asserted to ask two |

**What the code costs today** (read from the source, to be confirmed
by the tests):
- Data: every method is 1 round trip. `addTodoUnlessFull`,
  `listTodos`, `countTodos`, `updateTodo` and `deleteTodo` each send
  one statement. `setAllCompleted` and `deleteCompleted` send one
  batch of two (the write and the list, one transaction).
- Api: every todo route is 1 store call; each operation in
  `packages/operations/src/todos/` calls its port once. `GET /health`
  is 0.
- BFF: `/` is 1 api call (`GET /todos`, counts derived, deviation 5);
  `/active` and `/completed` are 2 (`GET /todos?completed=…` and
  `GET /todos/counts`, side by side). Each of the six actions is 1.
- So one `POST /todos` from the page is 1 api call × 1 store call ×
  1 round trip, plus the page's reload.

**The shape of the change**, subject to the questions:
- `fakeD1` also records each round trip (each `all`, `run` and
  `batch`), as `trips`.
- Three `budgets.test.ts`, one per level, each the record of that
  level's numbers:
  - `packages/data/d1/test/unit/budgets.test.ts`, keyed by `DbStore`
    method;
  - `apps/api/test/unit/budgets.test.ts`, keyed by `EndpointKey`, with
    a counting wrapper around the construct test's fake store;
  - `apps/bff/test/unit/budgets.test.ts`, keyed by page and action,
    with a counting fake binding.
- Each table is typed so that a new method, route or action with no
  budget does not compile: `Record<keyof DbStore, …>`,
  `Record<EndpointKey, number>`.

## The owner's answers (settled; do not ask again)

The questions were put to the owner in the session that wrote this
handoff. Every recommendation stands, in the owner's words where
quoted. The tour's "Why" table cites these.

| Question | Owner's answer |
|---|---|
| Q1, what the data level counts | Round trips to D1, with the batch's statement count beside them (`{ trips: 1, statements: 2 }`). Each `all` and `run` outside a batch, and each `batch`, is 1 trip. "A round trip is the cost on a Worker, the statement count is the cost on D1" |
| Q2, where the numbers are written | One `budgets.test.ts` per level, in the package that owns the counter. The cross-level column (api calls × store calls × trips) in the generated `entry-chains.md` is later. The data spec (row J) is the eventual home of the data level's numbers |
| Q3, the api level's counter | A counting wrapper on the construct test's `fakeDbStore`, moved to a shared test file both tests import, with each route sent one request through `constructRoutes`, so the real handler, validator and operation run. Not per operation in `packages/operations` |
| Q4, the BFF level | The three page loads and the six actions, each counted alone. The reload SvelteKit runs after an action counts against the load, not the action |
| Q5, the existing count assertions in `todos.test.ts` | Leave them |
| Q6, a decision | Record L36 and P67 (below) |

**L36, as the owner worded its intent:** budgets are for making cost
changes visible, not for forbidding them. A budget is the current cost
written down. A change to it is a deliberate edit, in the same commit
as the code that changed the cost, with its reason in the commit
message. The tests make cost changes visible; they do not forbid
them. Write L36 in the story's decisions list in that sense, and P67
in the profile notes as the pattern the profile should produce (three
budget tables, one per level, typed so a new unit without a budget
does not compile).

The owner's instruction: "Three test commits then the docs, each with
the doubled-call proof. Go." So the plan below runs without a further
