## Decisions (story entries L47 to L52)

Record these in `logbook/the-api-story.md` and the glossary in the
form the ledger uses. The wording below is the decision; the chapter
text is the agent's.

- **L47, the identity input rules.** The first rules in `rules.md`
  that are not about todos.
  - Email: trimmed, then lower-cased, then its rules. `lower-cased` is
    a new field modifier, defined as `String.prototype.toLowerCase` the
    way `trimmed` is defined as `String.prototype.trim`, and written
    after `trimmed` when both apply; the generator learns it. Rules:
    `email.length`, 1 to `EMAIL_MAX` = 254 (`length` form), and
    `email.shape`, `custom`: the WHATWG "valid email address", the
    definition `<input type=email>` applies, so the browser and the api
    never disagree. Not RFC 5322. The shape is ASCII, which keeps the
    `users.email` column's `CHECK (email = lower(email))` honest:
    SQLite's `lower()` folds ASCII only.
  - Password: never trimmed and never lower-cased; the field takes no
    modifier. Constants `PASSWORD_MIN` = 15 and `PASSWORD_MAX` = 128.
    15 is NIST SP 800-63B-4's minimum for a password that is the only
    factor, which this one is until slice E; ASVS 5.0 sets 8 and
    recommends 15. 128 is a request bound, not a hash-cost bound: with
    the pepper (L48) Argon2id hashes a fixed 32 bytes. No composition
    rules.
  - Sign-in applies only `password.given`, 1 to `PASSWORD_MAX`. The
    minimum is a set-time rule, written in slice C with the first input
    that sets a password (sign-up, change password); applying it at
    sign-in would turn any later raise of the minimum into a lockout.
  - Length is counted in UTF-16 code units, as the `length` form
    counts; NIST counts code points. The two differ only for astral
    characters near a bound. Accepted and recorded, not fixed.
  - The breached-password check is set-time, so it does not touch
    sign-in; it is carried to the first real deployment.
  - The design's "At least 12 characters" (sign-up and profile boards)
    becomes 15. Both are slice C's boards; the copy changes there.
- **L48, the credential store.** Table `credentials` in the identity
  database: `user_id`, `kind` (`password` today), `secret` (the
  Argon2id PHC string, with its parameters), `pepper_id`, `created_at`,
  `updated_at`; primary key `(user_id, kind)`.
  - Hashing: NFKC normalize, HMAC-SHA256 with the pepper (a Workers
    secret, named by `pepper_id`), then Argon2id via `@phi-ag/argon2`
    at m=19456 KiB, t=2, p=1, the `.wasm` imported as a module. The
    parameters and the current pepper id are constants in `business`.
  - The hasher is a port of the `auth` area (`verify`, `hash`,
    `needsRehash`), bound in the api. It is not a store: the data case
    stays SQL, and the CPU shows in the operation's budget.
  - The store reports what the row is; the operation decides
    `needs_rehash`, by comparing the row's parameters and `pepper_id`
    with the constants. The precedent is `sessions.find`, which reports
    an ended or expired session as it is and lets the gate decide
    liveness. A business constant does not move into data.
  - The rehash write is compare-and-set:
    `UPDATE credentials SET secret = ?, pepper_id = ?, updated_at = ?
    WHERE user_id = ? AND kind = ? AND secret = ?`, returning the
    change count, so two parallel sign-ins cannot race (L43's style).
- **L49, sign-in.** An `auth` operation; it reads `users` and writes
  only `auth` tables, so it is not a process (L41).
  - One read: `users JOIN credentials WHERE users.email = ? AND
    credentials.kind = 'password'`, the same shape as the gate's
    `sessions JOIN users`.
  - An unknown email runs `verify` against a fixed dummy PHC string at
    the current parameters, so the timing, status and body of "no such
    account" and "wrong password" are one (threats row 7, its sign-in
    half). A disabled user with the right password gets the same
    refusal and no session; its own state waits for D.
  - Rotation (L40, threats row 3): every sign-in starts a new row; a
    session the request already presented is ended in the same batch.
    The new row, the ended one and a due rehash go in one D1 batch.
  - The reply is `{ token, expiresAt }` in the envelope (L40). The BFF
    stores it as `__Host-sid` (unprefixed `sid` under `DEV`) and
    redirects to `/`. No `returnTo` in B (threats row 6 stays empty).
  - Email verification is not checked in B; C adds the `unverified`
    refusal. The seed marks its users verified now, so C changes
    nothing for them.
  - Login CSRF: a sign-in request carries no cookie, so the `channel`
    gate as written (cookie-bearing unsafe requests) does not see it.
    Amends L38: the `channel` check applies to every unsafe request
    that is not bearer, cookie or not. This stays route-free, as a gate
    must; the only unsafe non-bearer requests without a cookie are
    sign-in now and sign-up in C. Threats row 1 gains the case.
- **L50, sign-out.** Two operations, both `member`, scope `own`:
  - This device: ends the presented row, `ended_reason` `signed_out`.
  - Everywhere: ends every live row of the actor's user, this one
    included, `ended_reason` `signed_out_everywhere`. No
    re-authentication. ASVS 7.5.2's re-authentication protects the
    case where the caller survives: a cookie thief ends the owner's
    sessions and keeps his own. When the caller's session ends too, the
    thief gains nothing but a forced sign-in. Recorded in threats row
    10 as meeting the threat and deviating from ASVS's letter. Ending
    other sessions while keeping this one is not drawn; if it ever is,
    it needs C's re-authentication.
  - Both land on `accounts.shell.signed_out_notice`. Sign-out is a POST
    (no state change on GET, threats row 2). The BFF sends an expiring
    `Set-Cookie` and `Clear-Site-Data` as a courtesy; the api writes no
    `Set-Cookie` (L40). Authenticated pages answer
    `Cache-Control: no-store`, so Back after sign-out shows no list.
  - The `sessions` table gains `ended_reason` (L40 named it; slice A's
    migration did not add it).
- **L51, the sessions list.** The profile's Sessions section reads the
  actor's live sessions.
  - Captured once at `sessions.start`: `label` ("Firefox on Linux",
    from the forwarded `User-Agent`, by a small hand-written table, no
    parser dependency) and `city` (from `request.cf`, absent in dev).
    New columns.
  - Last active is coarse copy: "Active now" for this device, and
    otherwise day words from the last touch ("Active today", "Active
    yesterday", "Active 4 days ago"). The data cannot say more: a touch
    writes at most once per half idle window (12 h), so between touches
    the last request is known only to a 12-hour band. The touch
    interval and the steady-path budget (0 writes) stay as they are.
    The board's "Last active 3 hours ago" is example copy and changes.
  - `sessions.touch` also writes `touched_at` in its one `UPDATE`;
    last active reads it, never `idle_until` minus the window, which
    would break silently if the idle constant changed.
  - "This device" is the actor's session id, which the gate already
    attaches.
  - Amends `identity.md`'s "No call takes a scope": the sessions-page
    calls take the actor's scope, `{ ownerId }`.
- **L52, the sign-in throttle is the next stage.** The per-account
  failure counter with backoff, Turnstile verified in the BFF, the Rate
  Limiting binding keyed on the account and the WAF rule (threats row
  8) are carried, together, to stage 25, the stage that first exposes
  the app publicly. Not later. Reasons: a lab with two seeded users has
  nothing to protect; the counter adds a Refused row to sign-in, which
  is cheaper to write once than to amend; and its throttled state has
  no board yet. Notes for 25: key the counter on the normalized email,
  not the user id, so unknown emails throttle the same way and the
  counter does not enumerate; locks are temporary, never permanent.
  Row 8's Test cell stays empty and says why.

Glossary terms to add or amend: hasher (port), pepper, PHC string,
rehash, rotation, `ended_reason`, last active (coarse, and why);
Channel is amended by L49.
