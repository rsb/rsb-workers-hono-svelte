3. **Present a plan, then ask the owner** before any code. These are
   the questions to settle:
   - **The branch name**, for example `feat/slice-4-edit`.
   - **The PATCH body.** The PRD has `{ title?, completed? }`, with at
     least one. Does `ToggleTodoBody` become one `PatchTodoBody`? And
     is it one operation (`updateTodo` with a patch) or two (`toggle`
     and `rename`), behind one port method or two?
   - **The title rule in the API.** It is trimmed, 1–256 characters,
     and an empty title is a 422. The rule lives in business and is
     reused by the API's `validate.ts` and the BFF's `validate-title.ts`.
   - **The BFF `edit` action:**
     - A title empty after trim returns success without calling the
       API (19).
     - Over 256 is a `fail(422)` with the message and the typed text,
       so editing stays open with the text kept (4.7).
     - Any other failure shows "Something went wrong. Try again.".
   - **Without JS.** Editing is started by a double-click or by Enter,
     which needs JS. Should the page do anything without JS, or is
     editing JS-only?
   - **Blur saves** through `form.requestSubmit()`. Enter must not
     submit twice, once from the key and once from the blur that
     follows.
   - **Scenario 4.1 says the remove button is hidden,** but remove
     comes with slice 5. Is 4.1's remove part checked in slice 5, or is
     a hidden placeholder added now?
   - **The known edge case.** After a failed add, a toggle replaces
     `form`, and `NewTodo`'s derived `title` resets to "", so the typed
     text is lost. An `edit` action has the same problem. Fix it in
     slice 4 (for example, key each component's state to its own
     action), or leave it.
4. **Build in layers,** testing each tier:
   - contract;
   - business, if the rule moves;
   - operations;
   - d1;
   - API handler and route;
   - BFF `api/todos.ts` and the action;
   - UI;
   - e2e 4.1–4.9 in `apps/bff/e2e/edit.test.ts`.

   The e2e database is shared and has no remove yet, so the tests use
