# Handoff 22: the PRD tree, 2026-11-05

This handoff starts stage 22. It is a small stage whose only subject is
the workflow: the PRD becomes a tree of documents of known kinds, the
feature document is added as the layer between concept and use cases,
and the existing todo feature is written into it as the worked
example. Authentication, slice A, is handoff 23 and does not start
until this stage is reviewed; its feature documents are written here.

Handoff 11's Rules and Environment apply unchanged. Nothing in this
stage touches code under `apps/` or `packages/`; it touches `prd/`,
`design/`, the story and the glossary, and the two generators only
where a citation line changes.

## Why this stage exists

The planning chat produced the authentication design (handoff 23's
input) by going concept → decisions → research → explainer → handoff,
and then left "PRD lines" as a build item. That is the old habit: the
layer where the product is written in the user's terms was skipped
and left to the builder. The owner's observation that closes the gap:
a design board is not a picture of a screen; it is one view at one
state, and a view's state list is exactly what the chain below it
produces. So a feature document, the text twin of the design, is the
missing layer, and the PRD is the tree those documents live in.

## Decisions (story entries L44 to L46)

Record these in `logbook/the-api-story.md` and the glossary; add the
chapter "From idea to code" (below). The wording is the decision; the
chapter text is the agent's.

- **L44, the PRD is a tree.** `prd/<product>/` holds documents of
  known kinds: a short root (`<product>.md`: purpose, areas,
  product-wide limits, the error vocabulary, done per slice, deviations
  and amendments), `features/` (one per user job), `use-cases/<area>/`
  (one per operation), `rules.md`, `access.md`, `api.md`, and `data/`
  (one file per database, one entry per store call: the data cases).
  Each kind has its own address scheme and its own relationship to
  code; a feature changes the tree additively, and a change to an
  existing line is a recorded deviation. Nothing checks the root or
  the features; the join check already covers use cases, rules and
  the api, and the number of requirement lines no use case cites is
  reported, not failed.
- **L45, feature, view, state, board.** A feature is one job a user
  does, written in business terms, citing the layers below and never
  restating them. A view is one composition of behaviour; a state is
  what the chain produces for it, or what the BFF owns itself
  (pending, empty); a board is a view at one state under one viewport
  and theme. Ids are `<area>.<view>.<state>` and belong to the state;
  boards derive their names from them, `<view>.<state>.<viewport>.<theme>`,
  so a board name parses back to its state. A use case's Refused rows
  say which state shows them (`shows:`); the BFF's view maps each
  state to a template branch; the design's `state` prop enum is the
  feature's state list. Viewport and theme never appear in a spec.
  A state that needs a different composition is a different view.
- **L46, data cases are the data spec.** One file per database, one
  entry per store call: port method, use cases that use it, input and
  result, guarantee, failures, cost. SQL stays hand-written; the
  budgets tests read the cost lines; a conformance suite holds one
  test per guarantee. Chains cite the data cases they use. This
  retires backlog row J.

Glossary: feature, view, state, board, data case; amend PRD and
process.

## The chapter: from idea to code

Six layers, each answering one question, each written in order, each
citing the one above:
1. Concept: why and for whom; what changes for the user; what it is
   not. Lives in the planning chat and the explainer it produces; is
   linked from the story, never checked.
2. Decisions: how, within what constraints; tested against research.
   Story entries and the glossary.
3. Features: what the product does, seen from each view, in the
   user's terms. The design is their visual twin.
4. Use cases: what each operation promises (L30), citing features,
   rules and access.
5. Specs that are checkable: `rules.md`, `access.md`, `api.md`,
   `data/`. Generated into validators, the access property, the
   contract and the budgets' expectations.
6. Code, with little left to decide, and a handoff that names which
   of the above a stage adds.

What went wrong before: a ticket written from an idea skips layers 2
to 5, and every question those layers would have answered is answered
by the builder, silently, at the point of least leverage. The chapter
says this once.

## What this stage builds

1. `prd/_templates/feature.md`, `prd/_templates/data-case.md`, and
   `design/_templates/design-brief.md`. The three files are in this
   handoff's commit as written by the owner and Claude; the agent
   reads them, does not rewrite them, and proposes changes in the
   review tour.
2. `prd/todo/features/feature-todos-list.md`, the worked example, also
   written already. The agent checks it against the seven use cases
   and the first design's boards and reports any state the design
   shows that no use case produces, or the reverse. Fix the feature
   document, not the design.
3. `prd/todo/features/` for accounts, from the explainer
   (`logbook/reports/2026-11-05-22-auth-design.html`, section 7 and
   the design `design/2026-11-03-ui-accounts/`): `feature-accounts-sign-in.md`,
   `feature-accounts-sign-up.md` (with verification),
   `feature-accounts-profile.md`, `feature-accounts-users.md` (admin
   list, detail, disable), `feature-accounts-shell.md` (signed-out,
   member, admin; sign-out). The design's state wrappers are the state
   lists; where a wrapper has no producer in the chain, say so in the
   document's table as `open` rather than invent one. Slice A needs
   only the parts these name as its own; the rest wait.
4. The root thinned: `prd/todo.md` keeps Purpose, Source and licence,
   Constraints, Deviations, Envelope, Security, Shape, Database,
   Slices, Done, Out of scope, Amendments. Functionality (verbatim
   upstream) stays as the cited source. The API table moves to
   `api.md` if it is not already there; the Design section becomes a
   pointer to the feature; Acceptance scenarios move under the
   feature's Done, keeping their numbers so citations hold.
5. `prd/todo/data/app.md`: data cases for the seven todo store calls,
   from the stores as they are. Cost lines from the budgets tests that
   exist. (Identity's data cases are written in slice A with its
   tables.)
6. Use cases gain `shows:` on their Refused rows, citing state ids.
   The join check's citation parsing is extended only if `shows:`
   confuses it; otherwise nothing in tooling changes.
7. The story chapter, L44 to L46, the glossary, and the review tour at
   `logbook/reports/2026-11-05-22-prd-tree-review-tour.md`.
